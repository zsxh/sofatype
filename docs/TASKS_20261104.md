## 1. 拆分原则

1. 每个任务是完整闭环：编译 → 安装 → 运行 → 按验收点走查。
2. 模拟器（API 34）做逻辑回归。真机验收收敛到里程碑级任务。模拟器不覆盖性能预算、微信内核、真实遥控器。
3. 优先级：P0 先行，P1 随 M3 落地，P2 全部不做（见第 7 节）。
4. 「已完成」的唯一标准是真机验证（AGENTS.md）。汇报区分「已实现」与「真机已验证」。

- T28（T5 回归修复 bugfix）于 T5 归档后由户主走查触发，已完成（closed / 真机已验证）。

### 6.2 执行口径（PRD 决策之外的施工约定）

1. 真机启用输入法用 adb `ime enable` / `ime set`，不走电视系统深层菜单。
2. 更新 APK 下载到 cache 目录；安装确认后走系统安装器；装完或退出即清理（AGENTS.md 禁止事项 3）。
3. 模拟器阶段「手机端」用 Mac 浏览器手机模拟 + adb forward 验证；真机阶段用户主手机实测。
4. 性能口径用 logcat 计时佐证（决策 22），端到端时延用录屏核对。
5. 词库构建脚本若需 python3，先加入 `flake.nix` 再使用（HANDOFF 阶段 0 同类原则）。
6. git 提交一律由户主发起（AGENTS.md 禁止事项 8）。
7. 归档与派单流程（2026-11-04 户主拍板）：
   - T1 为特例：重审通过 → 提请户主验收 → 拍板后归档 → 才派 T2。
   - 其余非里程碑任务（T2/T3、T5~T11、T13~T18、T20~T26，及同类非里程碑 bugfix 任务如 T28）：评审通过即自动归档（issue 挪 `closed/`，任务状态按 6.2-8 口径标注），按依赖顺序直接派下一任务，不再提请户主。
   - 里程碑任务 T4/T12/T19/T27：真机节点，须户主配合与验收拍板后才继续；验收通过标「真机已验证」。T4 到点设备未连则按设备档案暂停并提示户主。
   - 升级条件（仍须报户主，经 lead）：PRD 冲突或需新拍板、评审超 3 轮、需要真机/户主配合。
8. 状态词口径（2026-11-04 户主拍板，2026-11-05 修订）：「已实现」= 评审通过 + 模拟器/模拟验证；「真机已验证」= 真机验证通过——里程碑任务经户主验收标注；已完成任务经真机验证后，由户主拍板回溯标注（2026-11-05 拍板回溯标注 T2/T3/T5/T28，取代原「不回溯修改其他任务状态」限制，见 PRD 决策 26）。
9. 评审执行方式（2026-11-05 户主拍板）：开发与评审由两个独立 agent 分担——开发 agent 负责实现、单元测试与本地测试；评审 agent 负责 code review、验收、审查、审计。盲审：评审 agent 只依据交付物评审，不接触开发 agent 的实现思路，沟通经 lead 中转。评审不通过附意见打回，修改后重审；同一任务评审上限 3 轮，超限报户主（对应第 7 条升级条件）。通过后按第 7 条口径归档。
10. 盲审交接载体（2026-11-06 户主拍板）：dev 交接内容直接以消息经 lead 中转给评审 agent，**不在仓库写 `*-handoff.md` 等交接文件**；交接要点由评审结论并入对应 issue 评审记录。既有 T9/T30 交接文件已按本条清理。
