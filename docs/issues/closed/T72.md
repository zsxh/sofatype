## 目标
<!-- 本 issue 交付的功能与结果，创建时写；与「改动」分开 -->

远程输入配对成功后，TV 与 H5 两端同显同一「连接代号」，替代现状两端硬编码「browser」的展示口径（现状：H5 自报 deviceName:'browser'，TV 端仅照显）。

代号 = [官方标 icon][设备类型]设备[两位序号] 胶囊，示例「微信设备 01」；同一客户端在时间窗口内刷新页面、断线重连、被顶替后再连，序号保持不变（保号）。

## 原因

户主反馈远程连接两端只显示「已连接 browser」，无法识别连接对象。连接代号提供可读标识；保号机制（2026-11-14 户主细化：LRU 内存表）避免刷新 / 重连即换号造成「连错电视」的困惑，顶替场景下各设备序号稳定可辨。

## 踩过的坑
<!-- 无则写「无」；实机新坑同时记入 docs/devices/ 对应档案 -->

1. **走查间隔未保活 → 屏保强杀链全链复现一次**（2026-11-15 Round 1 批次，坑 9 家族）：远程 WS 走查中途未挂保活，屏保链强杀 IME（进程消失 + default 夺回搜狗 + 远程服务死，`ps` + `dumpsys activity processes` 双证，H5 端 WS 断开）；恢复后即挂 5.5 分钟 DPAD 保活循环零复现。教训：远程 WS 走查**进远程模式即挂保活**，不等出事再挂（已补设备档案坑 9 补充）。
2. **H5 deviceKey 随 origin（含端口）失联**：TV 端远程服务每次重启随机换端口，H5 deviceKey 存 localStorage 按 origin 隔离——端口一变 deviceKey 即新生成、TV 端判新设备（序号 max+1）。保号类走查须同端口会话内完成；跨服务重启的端口变化在真实扫码场景语义上等于重新扫码（已补 local/DEV-GUIDE 备选通道坑 6）。
3. **观察项（需求侧待定性）**：macOS 桌面 Chrome UA 被判「苹果设备」——H5 判定正则有意含 Macintosh（Mac 上的浏览器归苹果设备）；browser 分支验证需用 Windows UA。2026-11-15 户主拍板维持现状（已补 PRD 决策 61）。
