# issues · 变更记录规范

单次代码 / 软件变更的唯一详细记录。本文是规范与模板；具体变更看各 issue 文件。

## 规则

1. 一个代码 / 软件变更（功能、bug fix、构建脚本）= 一个 issue 文档。纯文档调整不建 issue。
2. issue 与 TASKS 任务一一同名同编号：任务 T5 对应本目录 `open/T5.md`。编号即任务编号，从 1 开始、全局递增，closed 不复用。
3. 目录：`open/` = 进行中；`closed/` = 已验收关闭。
4. 生命周期（2026-11-04 拍板：issue 文件预建，目标、改动与原因创建时写明）：
   - 全部 issue 文件预建于 `open/`，创建时写明目标、计划改动与原因；开工后按实际实现更新「改动」，验收结论填「验收」；
   - 任务开工时填充对应 issue 正文，TASKS 对应任务状态改「进行中」；
   - agent 完成实现并通过模拟器 / 模拟过程验证后，通知户主验收；
   - 户主拍板通过后，文件挪入 `closed/`，同时更新文件内状态行与关闭日期；
   - 已 closed 的功能出回归：不重开旧 issue。TASKS 追加新任务行（编号顺延），新建同名 issue 文件。
5. bug fix 在 TASKS 追加任务行并建同名 issue，类型标 `bugfix`。
6. 「目标」与「改动」分开写：「目标」描述本 issue 交付的功能与结果（做什么、交付什么）；「改动」只写具体执行内容（改哪些文件 / 模块、怎么改）。目标结果导向，改动执行导向，两者不混写。

| 创建 / 关闭 | YYYY-MM-DD / — |

## 目标
<!-- 本 issue 交付的功能与结果，创建时写；与「改动」分开 -->

<!-- 具体执行内容：改哪些文件 / 模块、怎么改 -->

## 验收
<!-- 区分「模拟器已验证」与「真机已验证」；户主验收结论记录在此 -->
