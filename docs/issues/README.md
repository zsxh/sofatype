# issues · 变更记录规范

单次代码 / 软件变更的唯一记录，**issue 即需求**：拍板口径、方案评估、验收结论都在 issue 内。本文是规范与模板；具体变更看各 issue 文件。

> **2026-11-19 修订（户主拍板）**：`docs/PRD_20261104.md`（需求基线，决策 1~78）与 `docs/TASKS_20261104.md`（施工拆解）已归档冻结、禁止更新（见各文件顶部横幅）。任务制废止，新需求一律建 issue；历史决策 1~78 见归档 PRD 第 12 章，其后拍板不再使用决策编号，引用一律用 issue 号。存量 issue（closed）内容不追溯。

## 规则

1. 一个代码 / 软件变更（功能、bug fix、构建脚本）= 一个 issue 文档。纯文档调整不建 issue。同一次拍板、同主题的多条口径可合一个 issue（「需求与口径」分条列）；跨主题的拍板拆开各建。
2. **issue 即需求**：拍板口径写入 issue「需求与口径」节，验收对照此节。归档 PRD 是 v1.2 基线快照，只可只读引用；引用基线条款前先核对归档 PRD 第 12 章决策修订链与相关 issue，条款可能已被后续拍板修订或废止，冲突时以最新拍板 issue 为准（新压旧）。对基线条款的修订须在 issue 中注明被修订条款；引用基线必须带具体文件名（如 `docs/PRD_20261104.md`），不用通配符。
3. **新建 issue（取号）前必须经户主拍板**，agent 不得自行立项建档；立项 ≠ 开工，开工另等户主指令。处理任何 issue（开工实现、修复、验证等）之前必须先通知户主、询问是否处理，只有户主同意了才能进行，除非户主显式要求执行。
4. 目录：`open/` = 进行中；`closed/` = 已验收关闭。
5. 生命周期：
   - 户主拍板 → 取号建档，创建时写「背景」「需求与口径」「方案评估」（预评）「验收」（口径清单）；
   - 户主批准开工 → 实施，实施后在「方案评估」回填实际改动清单（一行一个文件 / 模块）、「验收」补结果；
   - agent 完成实现并通过模拟器 / 模拟过程验证后，通知户主验收；
   - 户主拍板通过 → 文件挪入 `closed/`，同时更新文件内状态行与关闭日期；issue 关闭后冻结；
   - open 期发现本 issue 实现缺陷：本 issue 内修复，「追加补充」留痕，不另立；已关闭后发现 → 另立新 issue；
   - closed 不重开；回归一律重新取号、新建 issue。
6. bug fix 同样取号建档，类型标 `bugfix`。
7. 坑分流（issue 不设坑节）：实机 / 设备坑入 [`docs/devices/`](../devices/) 对应设备档案（一机一档，细节唯一维护处）；共性坑（实现层 / 框架层 / 走查方法，跨设备跨环境）入 [`docs/HANDOFF.md`](../HANDOFF.md) 坑清单，新增条目一行自包含（说清坑本身与规避法，可指向设备档案）；本地开发环境坑按 [`AGENTS.md`](../../AGENTS.md)「文档同步」条款处理。
8. 「追加补充」节 append-only：带日期逐条追加，只追加不改写；判据——不改变已拍板行为语义、不推翻验收结论的才可追加，推翻性、超范围的一律另立新 issue。
9. 拍板决策详情入对应 issue；[`docs/HANDOFF.md`](../HANDOFF.md) 决策速查表按 issue 号登记一行。
10. 取号：**新建 issue 前必须先读本目录 [`NEXT-ID.md`](NEXT-ID.md)**，取「下一个可用编号」；取号后立即回写该文件（下一个编号 +1、最后已用编号、最近更新），先写回再填充正文。取号簿与目录实况冲突时，以目录实况为准，先修正取号簿再取号。

## 节职责

- **背景**：首行写拍板日期与渠道；再写根因、现状问题；无前置背景可删整节。
- **需求与口径**：拍板的行为口径（What）——行为应该是什么；修订基线须注明被修订条款。验收对照此节。
- **方案评估**：实施前评估影响范围（模块 / 文件）、回归面（哪些既有行为须不回归）、风险与取舍；实施后回填实际改动清单（一行一个文件 / 模块，不展开实现细节，细节归 git）。
- **验收**：写验证手段与预期观测（模拟器场景 / 单测用例 / 真机步骤，trace / dumpsys / 截图），与「需求与口径」不重复；执行后补结果与户主结论，区分「模拟器已验证」与「真机已验证」。
- **追加补充**：实施中的新问题与新口径，append-only（规则 8）。
