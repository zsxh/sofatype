## 踩过的坑

### 坑 1：硬件 64 位、系统 32 位——装 APK 必须选 `armeabi-v7a`

最容易踩的坑：`/proc/cpuinfo` 显示 AArch64，容易被误导去下 arm64 包。实际 Android 用户空间只有 32 位，装纯 `arm64-v8a` 的包会直接失败：

```
INSTALL_FAILED_NO_MATCHING_ABIS
```

只能装 **`armeabi-v7a`** 的包（`universal`、`noarch` 也可以）。含原生库的包才受此限；纯 dex 的包（APK 无 `lib/` 目录）不受限，可装（拍板见 PRD 决策 23）。装前复核：

```bash
unzip -l <apk> | grep -oE 'lib/[a-z0-9_-]+/' | sort -u   # 无输出 = 纯 dex 包，可装；有输出时只允许 armeabi-v7a
adb shell getprop ro.product.cpu.abilist
```

### 坑 2：无线 ADB 传大文件必卡死——别用无线链路传 APK

2026-10-28 实测：无线传 7.2 MB APK，`adb install`、`adb push`、HTTP + `wget` 全部卡死在几百 KB，吞吐仅 **0.2–2 KB/s**（`adb install` 超 300 s 只写入约 850 KB；64 KB push 传输瞬间完成但整条命令耗时 16.4 s；HTTP 下载仅约 217 B/s）。

排查后**已排除**以下原因（不要重新验证）：

- APK 架构：APK 含 `armeabi-v7a`，与本机匹配（见坑 1）。
- adb 版本 / 连接状态：`adb shell echo hi` 仅 0.35–0.9 s，控制通道正常；`kill-server` 重连无效。
- 电视无线网卡：电视 → 路由器 / 互联网 ping 均 0% 丢包、2–8 ms。
- 路由器整体故障：Mac → 路由器同样正常。
- MTU 黑洞：1472 B 探测 0% 丢包；丢包率随包大小无规律（800 B→20%、1400 B→40%、1472 B→0%），属随机突发丢包。

**真正的故障点：Mac ↔ 电视的 2.4 GHz 无线链路**——小包秒回，持续传输必塌：

| 路径 | 丢包 | 延迟 | 结论 |
|---|---|---|---|
| **Mac → 电视** | 小包 0%，**大包 20–40%** | 3.7–**118** ms，抖动极大 | **异常** |
| Mac → 路由器 | 0% | 2.1–10.2 ms | 正常 |
| 电视 → 路由器 / 互联网 | 0% | 2.3–4.6 / 4.2–21.5 ms | 正常 |

**结论：在这台电视上装 APK，不要走无线 ADB 传大文件**（限 2026-10-28 链路状态；2026-11-04 复测见下方），按省事程度 / 成功率排序改用：

**2026-11-04 复测：同地址传输未复现塌陷，APK 已装上。**

- 时间 / 路径：2026-11-04 16:43（+0800）。无线 adb 地址 `192.168.1.210:5555`，单次 connect 成功（项目密钥 `/.adbhome/.android/`，电视已信任，免授权）。户主已接线；电视当前走有线还是 Wi-Fi 未验证（授权口径只 connect 一次，未再连查接口）。
- 传输：778 KB 纯 dex 包（T1 产物，无 `lib/`）`adb push` 0.003 s 传完，adb 自报 **233.8 MB/s**；含通道建立全程 47 s（同口径含握手的平均速度约 25.7 KB/s，瓶颈不在链路）。
- 安装：`pm install` Success。`com.sofatype.ime` 0.1.0(1) 已装机保留（T4 使用）。push 临时文件已按名清理，adb server 已停，5037 无监听。
- 对比：与 2026-10-28（0.2–2 KB/s、必卡死）完全不同，链路状态已变化。若当时故障确因 2.4 GHz 链路，本次结果支持「插网线绕开」推断；接口归属未确认，不做定论。

1. **插网线（最推荐）**：任一端走有线即可绕开 2.4 GHz 链路。
2. **U 盘安装**：APK 拷进 U 盘插电视，用电视自带文件管理器安装，不依赖网络。
3. **USB 数据线 adb**：电视 USB 口连 Mac，速度快且稳定。
4. **换 5 GHz**：路由器与电视都支持时，把电视切到 5 GHz（2.4 GHz 信道 13 本就是干扰最重的频段）。
5. `wget -c` 断点续传硬扛——按当时速度需 1–10 小时，仅最后手段。

## 还存在的已知问题

### 2.4 GHz 无线链路大流量塌陷——根因未证实，问题未解决

坑 2 只定位到「故障点在 Mac ↔ 电视的无线链路」，具体根因尚未证实，截至 2026-10-28 问题未解决（当时的 APK 最终未装上）。剩余假设按可能性排序：

1. **电视 Wi-Fi 省电模式（PSM）**：电视在 AP 侧长期休眠/唤醒、只在 DTIM 收包，持续传输时 TCP 反复超时导致吞吐塌陷——「小包秒回、大包卡死」与实测现象最吻合。
2. **2.4 GHz 信道 13 拥塞**：两端同信道、20 MHz、同一 AP，争用空口时间；邻居网络干扰放大突发丢包。当时链路：电视 RSSI -35 dBm / 链路速率 72 Mbps，Mac 802.11n / -53 dBm / 发送速率 78。
3. **AP 客户端间转发（client-to-client）瓶颈**：两台设备到路由器都正常，但客户端互访需经 AP 内部交换，部分家用 AP 对这条路径有额外瓶颈或限速。
4. **Mac 侧 802.11n 协商速率余量不足**：20 MHz / 78 Mbps，遇重传吞吐迅速下降。

**下一步验证方向**：插网线或切 5 GHz 后复测大文件传输——若恢复正常，可坐实 2.4 GHz 链路问题，再逐项验证上述假设；若仍有问题，则要重新审视 AP 转发路径。

**2026-11-04 复测更新**：同地址、同口径复测，778 KB 传输瞬间完成（adb 自报 233.8 MB/s，见坑 2 复测段），塌陷未复现，APK 已装上（`com.sofatype.ime`）。结果指向链路状态变化（户主已接线；电视接口归属未验证）。下一步：T4 真机部署时用 `ip route` 确认电视当前默认接口，闭环「有线 vs 无线」归因。归因未闭环前，大文件传输仍优先走有线 / USB（原推荐顺序不变）。

**仍然不要做**：反复重试 `adb install` / `adb push`（每次从头传，必然重复卡死）；修改 MTU（已排除 MTU 问题）。
