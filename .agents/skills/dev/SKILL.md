# 双 Agent 开发与审查编排

## 1. 目标

以「实现 — 黑盒审查」的双 Agent 闭环，完成 PRD 中一个未完成任务，直至审查通过或触发轮次上限。

## 2. 角色命名（创建子 Agent 前必须先命名）

本 Skill 涉及两个子 Agent，**在创建（spawn）之前即以下述名称与角色标识它们**；此后所有派发、交接、反馈、轮次记录、日志与用户汇报，一律使用该名称指代，不使用「Agent 1 / Agent 2」这类泛称。

| 名称（spawn 时使用） | 角色 | 一句话职责 |
|---|---|---|
| `dev` | Senior Software Engineer | 实现功能、编写单元测试、本地自测通过后交付 |
| `review-qa` | Code Reviewer & QA | 黑盒 Code Review、验收核验、真机验证(若有明确指出)，给出 PASS/REJECT |

创建子 Agent 时，名称与角色描述必须一并传入；若运行环境支持，应同时传入角色边界与本文第 4 节的信息隔离约束。**两个子 Agent 均为独立实例，互不共享上下文。**

## 3. 前置条件（硬性，缺一不可）

- [ ] 两个子 Agent 在开始任何工作前，**必须先阅读 `local/` 目录下的本地开发指南**（构建、运行、测试、真机部署、代码规范）。
- [ ] 已定位 PRD task 列表，并能识别任务状态（未完成 / 进行中 / 已完成）。
- [ ] 已确认任务的验收标准（Acceptance Criteria），若 PRD 未写明，先向用户澄清。

## 4. 信息隔离规则（关键）

**`dev` 的实现思路不得透露给 `review-qa`。**

- `review-qa` 只允许接收：PRD 任务原文、验收标准、代码产物、测试产物、运行/部署方式。
- `dev` 的以下内容**禁止**进入交付：设计思路、方案选型说明、实现心路、内部备注、调试过程记录、自评。
- 交付内容以「黑盒可验证」为准：`review-qa` 应能只靠需求 + 产物独立判断对错。
- 打回时反馈由 `review-qa` 单向给出，`dev` 不得反向向其解释设计理由。

## 5. 交接原则（不约定格式，由 Agent 自行决定载体）

**不规定交接包模板、字段名或文件格式。** 交接形态（文档、清单、提交说明、会话消息等）由 `dev` 自行决定，但必须满足：

1. **自足**：`review-qa` 仅凭交接内容 + 仓库产物，即可完成 Code Review、验收与真机验证，无需追问。
2. **可执行**：给出能复现的本地运行/测试命令与真机部署方式，环境前提说清楚。
3. **可追溯**：指明改了哪些文件、对应哪条验收标准、单测与本地自测的实际结果（通过/失败，非声称）。
4. **只陈述事实**：描述「做了什么、怎么跑、结果如何」，不描述「为什么这么设计」。判断"是否满足需求"的权力完全留给 `review-qa`。
5. **零猜测**：不确定的信息不写、不美化；缺失项显式标注，交由 `review-qa` 判定是否构成阻塞。
6. **单一入口**：一次交接对应一次明确的审查请求（含任务标识与轮次），不分散在多处让对方自行拼凑。

`review-qa` 的反馈同样不限定格式，但须满足：结论明确（`PASS`/`REJECT`）、失败项可定位（对应哪条验收标准、复现方式、期望行为、严重程度）、建议与阻塞项分离。

## 6. 工作流程

### Phase 0 — 选任务（编排方）
1. 读取 PRD task 列表。
2. 选出一个**未完成**任务，优先级：显式优先级 > 依赖关系（无未完成前置）> 列表顺序。
3. 向用户播报所选任务与验收标准。

### Phase 1 — 创建子 Agent
1. 以名称 `dev` 创建实现方子 Agent，角色 = Senior Software Engineer。
2. 以名称 `review-qa` 创建审查方子 Agent，角色 = Code Reviewer & QA。
3. 分别下发：角色职责、`local/` 指南路径、"必须先读指南"的硬性要求、第 4 节信息隔离约束。
4. 向 `dev` 额外下发：任务原文 + 验收标准 + 第 5 节交接原则。

### Phase 2 — `dev` 实现
读 `local/` 指南 → 实现功能 → 写单测 → 本地自测全绿 → 按交接原则交付产物。

### Phase 3 — 交接
`dev` 提交产物，**主动通知 `review-qa` 开始审查**（附任务标识与轮次）。

### Phase 4 — `review-qa` 审查
读 `local/` 指南 → Code Review → 验收核验 → 真机验证 → 输出结论。

### Phase 5 — 判定
- `PASS` → 归档结果，向用户汇报，任务标记完成，流程结束。
- `REJECT` → 将反馈打回 `dev`，进入下一轮（Round += 1），回到 Phase 2。
- 第 3 轮仍 `REJECT` → **立即停止并通知用户**，附全部 3 轮反馈摘要与当前产物状态，由用户决策。

## 7. 轮次与终止条件

| 条件 | 动作 |
|---|---|
| Round 1 通过 | 完成 |
| Round 2 通过 | 完成 |
| Round 3 通过 | 完成 |
| Round 3 仍不通过 | 上报用户，终止 |

- 轮次上限：**3**。
- 每轮记录：轮次号、`review-qa` 结论、反馈要点、`dev` 修改摘要（记录形式不限）。

## 8. 对用户的输出

始终以子 Agent 名称指代双方（`dev` / `review-qa`）。

- **开始**：所选任务、验收标准、轮次上限、已创建的两个子 Agent 名称。
- **每轮结束**：轮次、结论、关键问题（1 行）。
- **超限**：全部轮次反馈汇总 + 阻塞点 + 建议决策选项（换任务 / 降级需求 / 人工介入）。
- **最终**：任务、轮次、验证结果（含真机验证结论）。

## 9. 约束清单

- [ ] 两个子 Agent 已在创建前命名为 `dev` 与 `review-qa`，且全程以此指代。
- [ ] 两个 Agent 均已读 `local/` 指南。
- [ ] 任务确为 PRD 中「未完成」状态。
- [ ] 每轮交接满足第 5 节全部原则，且不含实现思路。
- [ ] 轮次计数准确，第 3 轮失败必须上报，不得自动进入第 4 轮。
- [ ] 任何一方信息不足时，向编排方提问，不得臆测需求。
